# Технический, продуктовый и UI-аудит MULTI-CHEF (56-й круг)

**Дата:** 2026-09-15
**Область:** ID/ULID generation patterns
**Артефакты:** этот отчёт + обновлённый `docs/audit/FIX-PLAN.md`

---

## TL;DR

В `packages/database/prisma/schema.prisma` зафиксировано: «id: ULID-style
String @id (26 chars), generated by application». На практике:

- 3 копии самописной функции `ulid()` в seed/import-скриптах, и ни одной
  в `apps/api/src` (где создаётся 95% записей).
- Реализация `randomBytes(13).toString('hex')…` — это **не ULID**: нет
  time-prefix, не Crockford base32, не монотонная сортировка. Название
  вводит в заблуждение.
- В web-приложении параллельно используется UUID v4 (через
  `crypto.randomUUID()`) для idempotency-keys / session-ref'ов — формат
  ID в БД не совпадает с форматом ID в client-side storage.

## Технические находки (56-й круг)

### T56-A · 🟠 P2 — Три копии функции `ulid()`, и все три — не ULID

**Где:** `packages/database/src/seed/index.ts:44-46`,
`packages/database/scripts/import-recipes.ts:22-24`,
`packages/database/src/seed/recipes/index.ts:32-34`.

**Симптом.** Все три файла содержат одинаковую функцию:

```ts
function ulid(): string {
  return randomBytes(13).toString('hex').toUpperCase().padEnd(26, '0').slice(0, 26);
}
```

Эта реализация **не соответствует RFC для ULID**:

1. Нет 48-битного timestamp в первых 10 символах — ID не сортируется
   по времени создания, что является главной причиной использовать ULID
   вместо UUID.
2. Hex-алфавит (`0-9A-F`), а не Crockford base32 (`0-9A-HJKMNP-TV-Z`),
   то есть плотность символа в 1.6 раза ниже → выше коллизии при том
   же размере строки.
3. `padEnd(26, '0')` для 13 случайных байт (26 hex-символов уже даёт
   ровно 26) — избыточно. Если случайно `randomBytes(13)` вернёт байт
   с leading zero, `padEnd` ничего не добавит, и ID получится 24 символа
   вместо 26 — Prisma примет (id — String без `.length()`), но другие
   сервисы, валидирующие `.length === 26`, сломаются.

**Почему важно.**

- **DRY**: 3 копии одной и той же логики — если формат надо сменить
  (например, перейти на настоящий ULID), придётся менять в 3 местах.
- **Корректность**: при `randomBytes(13)` коллизия 50% при ~2^65 ID
  (по парадоксу дней рождения). У настоящего ULID с монотонным
  счётчиком в пределах миллисекунды — коллизия исключена.
- **Аналитика**: в БД 300+ записей, индекс B-tree на
  `Recipe.id`-колонке не использует time-prefix для сортировки →
  `ORDER BY id` не даёт временной порядок.

**Гипотеза фикса.**

1. Подключить `@paralleldrive/ulid-next` (drop-in, tree-shakeable,
   ~1 kB).
2. Завести `packages/id/src/index.ts` с одной функцией `newUlid()`,
   реэкспортировать через `@multichef/config` или отдельный
   `@multichef/id`.
3. Все три копии заменить на импорт.

### T56-B · 🟠 P2 — API не имеет своего `ulid()`-хелпера

**Где:** `apps/api/src/**/*.ts`, схема: `model User { id String @id }` и
ещё 30+ моделей с тем же паттерном.

**Симптом.** В схеме `id` объявлен как `@id` без `@default(cuid())` /
`@default(uuid())` / `@default(dbgenerated("gen_random_uuid()"))` —
то есть Prisma не генерирует ID на insert'е. Все контроллеры, видимо,
полагаются на app-level `ulid()`, но в `apps/api/src` такой функции
нет. Поиск по `apps/api/src` для слова `ulid` пуст.

Это значит, что при `prisma.user.create({ data: { … } })` без явного
`id` будет ошибка:

```
Argument `id` is missing.
```

Либо (что вероятнее и опаснее) — где-то в API всё-таки есть
генерация, но она размазана по контроллерам и не имеет единого
контракта. Без аудита всех `*.create()` и `*.upsert()` нельзя быть
уверенным, что ID действительно всегда ULID-shaped.

**Почему важно.**

- Если ID генерируется на стороне Prisma через `@default(cuid())`, то
  в БД попадают cuid'ы — формат ID разный у seed vs API записей,
  ломается любая логика сравнения/парсинга.
- Если app-уровень генерирует ID, нет единого места для добавления
  префикса (например, `usr_…`, `rec_…` для type-safe ID — паттерн,
  используемый в Stripe).

**Гипотеза фикса.** Либо (а) `packages/id/src/newUlid()` +
использование в API; либо (б) сменить Prisma-схему на
`@default(dbgenerated("gen_random_uuid()"))` (pguuid) для всех
моделей и **убрать app-level генерацию**. Вариант (б) убирает целый
класс ошибок «забыл передать id» и согласовать между API/seed/web.

### T56-C · 🟡 P3 — Web использует UUID v4, бэкенд — «ULID»-hex

**Где:** `apps/web/src/lib/auth-client.ts:80`,
`apps/web/src/lib/rescue-session.ts:23`,
`apps/web/src/lib/recommendations-client.ts:193`.

**Симптом.** На клиенте для idempotency-key и session-ref'ов:

```ts
const c = globalThis.crypto;
if (c && typeof c.randomUUID === 'function') return c.randomUUID();
return Math.random().toString(36).slice(2); // fallback в rescue-session
```

UUID v4 имеет другой формат (36 симв, дефисы) и алфавит, чем
"ULID"-hex из БД (26 симв). Если в логах/API смешиваются, разработчики
должны помнить конвенцию «ULID-shaped — для записей, UUID v4 — для
request-id». Это когнитивная нагрузка без явной выгоды.

**Гипотеза фикса.** Унифицировать через `@multichef/id` — одна функция
`newUlid()`, доступная и в SSR (Node), и в браузере (ESM).

### T56-D · 🟡 P3 — Fallback на `Math.random()` в `rescue-session`

**Где:** `apps/web/src/lib/rescue-session.ts:23`.

**Симптом.**

```ts
function newRef(): string {
  const c = globalThis.crypto;
  if (c && typeof c.randomUUID === 'function') return c.randomUUID();
  return Math.random().toString(36).slice(2);
}
```

`Math.random()` не криптографически стойкий. В контексте `rescue-session`
это используется как sessionStorage key — не security-critical, но при
большом числе параллельных вкладок (10+) коллизия `Math.random()`-based
ключа становится заметной (`base36.slice(2)` — 11 символов, ~52 бита
энтропии, при 1 млн ключей birthday-парадокс даёт ~3 коллизии).

В современных браузерах `crypto.randomUUID` есть всегда — fallback
мёртвый код, но он врёт: создаёт впечатление, что код работает в
legacy-окружениях.

**Почему важно.** Несоответствие кода и реальности: либо удалить
fallback, либо перейти на ULID (`newUlid()`), который в браузере
выдаёт 128-битную base32 строку без коллизий.

**Гипотеза фикса.** Заменить `newRef()` на:

```ts
import { newUlid } from '@multichef/id';
export const newRef = (): string => newUlid();
```

## Подтверждённые здоровые паттерны

- `generateIdempotencyKey()` в `auth-client.ts:73-87` — корректная
  ручная реализация UUID v4 с правильными битами версии/варианта,
  fallback на `getRandomValues`, и только потом `Math.random()`.
- Prisma-схема использует `@id String` без `@default(...)` — это явно
  передаёт контракт «app генерирует ID», что лучше, чем неявный
  Prisma-default.
- ID хранятся как `String`, не `Bytes` — JSON-сериализация в API
  работает без base64.
