# ADR-0023: Row-Level Security — изоляция тенантов на уровне Postgres

## Статус

Принято (фаза 0). Включение — фазированное, после внедрения tenant-контекста
в слое данных (см. «План внедрения»).

## Контекст

AUDIT-REPORT.md круг #3 (T4, VERIFICATION.md §T4): RLS выключен на всех 25
таблицах (`relrowsecurity = f`) — изоляция household'ов существует только на
уровне приложения (Prisma `where: { householdId }`). Любой SQL-доступ с
правами `multichef` видит все данные всех семей.

Prisma не умеет RLS нативно и не устанавливает сессионные переменные —
стандартная связка «Prisma + RLS» требует явного управления контекстом
сессии. Дополнительное ограничение: `mc003_initial` создаёт расширения,
поэтому свежие окружения разворачиваются суперпользователем, а таблицами
владеет `multichef` — владелец обходит RLS, если не включён `FORCE`.

## Решение

1. **Контекст сессии.** Каждая транзакция API устанавливает локальные
   (транзакционные) настройки:
   - `SELECT set_config('app.household_id', $householdId, true)`
   - `SELECT set_config('app.user_id', $userId, true)`

   `set_config(..., true)` = `SET LOCAL`: действие ограничено транзакцией,
   пул соединений безопасен.

2. **Политики.** На каждой тенант-таблице:

   ```sql
   CREATE POLICY tenant_isolation ON <table>
     USING (<ключ> = current_setting('app.<ключ>', true))
     WITH CHECK (<ключ> = current_setting('app.<ключ>', true));
   ```

   `current_setting(..., true)` возвращает NULL без контекста → сравнение
   NULL → **fail-closed**: запрос без установленного контекста не видит
   ни одной строки. Для вложенных таблиц (Day/Entry/Task/Item/Portion) —
   `EXISTS`-подзапрос к корневому агрегату. Каталог (Ingredient*, Recipe*,
   StorageRule) — публичный read-only, без политик.

3. **Роли.** Рантайм-пользователь владеет таблицами → обязателен
   `ALTER TABLE … FORCE ROW LEVEL SECURITY` (иначе владелец обходит RLS).
   Миграции выполняются владельцем/суперпользователем как сейчас.

4. **Фазы.**
   - **Фаза 1 (эта миграция, инертно):** `CREATE POLICY tenant_isolation`
     на всех тенант-таблицах. Политики без `ENABLE` не действуют — прод
     не затронут, но политика уже зафиксирована в схеме и код-ревью.
   - **Фаза 2:** слой данных (`@multichef/database`) получает
     `withTenantContext(householdId, userId, fn)` и все сервисы
     переводятся на транзакционный вызов; интеграционные тесты
     прогоняются с включённым RLS на `multichef_test`.
   - **Фаза 3 (активация):** миграция `ENABLE` + `FORCE ROW LEVEL
SECURITY` на целевых таблицах + приёмочные SQL-пробы
     (cross-tenant → 0 строк).

## Тестирование

- SQL-проба изоляции (эталонная, фаза 1): включить RLS на пилотной
  таблице в тестовой БД, под контекстом A видеть строки A, под
  контекстом B — 0, без контекста — 0. Реализовано в
  `packages/database/src/__tests__/rls-policies.integration.test.ts`.
- Регресс: вся существующая интеграционная suite обязана остаться
  зелёной (RLS инертен до фазы 3).

## Риски и откат

- Включение без контекст-слоя = мгновенная «пустая БД» для API — поэтому
  активация вынесена в фазу 3 и блокируется код-ревью на Phase 2.
- Производительность: `SET LOCAL` в транзакции — околонулевая цена;
  политики-подзапросы на корневых агрегатах используют PK-индексы.
- Откат: `ALTER TABLE … DISABLE/NO FORCE ROW LEVEL SECURITY` — мгновенно и обратимо;
  политики остаются в схеме.

## Последствия

- Утечка cross-tenant через забытый `where` в Prisma становится
  невозможной на уровне БД (fail-closed).
- Прямые SQL-инструменты оператора для отладки должны устанавливать
  контекст явно (или подключаться суперпользователем).
