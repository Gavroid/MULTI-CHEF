# ADR-0026 — Accept рекомендации: генерация плана через job-поллинг (вариант b)

**Дата:** 2026-09-19
**Статус:** принято (R20-fixes, задача 4 / F2)
**Контекст:** AUDIT-R20 F2 — accept-флоу на проде работал на моке
(`NEXT_PUBLIC_USE_MEALPLAN_MOCK=1` в прод-бандле), реальный контракт был
сломан дважды: `MealPlanSetupDtoSchema` (non-strict) молча стрипал
`recipeId/servings`, а ответ `{jobId, deduplicated}` не матчится с
клиентским `{mealPlanId, shoppingListId}`.

## Решение

Вариант (b) — job-поллинг:

1. `POST /api/v1/meal-plans` принимает `MealPlanSetupDto` (дефолты:
   7 дней, 3 приёма/день, 2 чел.) и ставит джобу генерации плана
   (`202 {jobId, deduplicated}`) — существующий пайплайн без изменений.
2. Клиент (`acceptRecommendation`) поллит `GET /api/v1/jobs/:id`
   (интервал 1.5 c, дедлайн 120 c) до `COMPLETED`/`FAILED`.
3. После `COMPLETED` клиент читает `GET /api/v1/meal-plans/active` и
   возвращает `{mealPlanId}`; список покупок создаётся воркером вместе
   с планом (клиент навигирует на /shopping, где читается активный).
4. Мок (`usesMealPlanMock`, `NEXT_PUBLIC_USE_MEALPLAN_MOCK`) удалён
   из клиента и прод-env.

## Почему не вариант (a) — точечный план из recipeId

`POST /meal-plans` с `recipeId/servings` (точечный план «готовлю это
сегодня») продуктово точнее, но требует: расширения setup-контракта,
отдельной ветки генератора (план на 1 день вокруг фиксированного
рецепта + shopping list из ингредиентов рецепта). Это отдельная
продуктовая задача; вариант (b) устраняет мок и чинит флоу сейчас.

## Следствия / trade-offs

- Принятое блюдо НЕ пинится в сгенерированном плане — план это
  недельная генерация. Зафиксировано как известный trade-off.
- `MealPlanSetupDtoSchema` остаётся non-strict (серверstrip-поведение),
  клиент отправляет только документированные поля.
- Accept блокирует UI до ~2 минут (дедлайн поллинга); типовой прогон
  джобы генерации — 30–60 c.
