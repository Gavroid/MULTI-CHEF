## 2. Fixture-фиксация расчётов (антирегрессия домена)

Все вычислительные модули тестируются против **зафиксированных ожиданий**, а не пересчитанных «тем же кодом» значений.

| Fixture | Вход | Зафиксированное ожидание |
| --- | --- | --- |
| `nutrition-basic` | 100 г куриного филе (110 ккал/23/2/0 на 100 г) | 110 ккал, Б 23, Ж 2, У 0 |
| `nutrition-recipe` | рецепт: филе 200 г + рис сухой 80 г + масло 10 г, servings=2 | точные значения на порцию, вычисленные вручную и записанные в файл |
| `nutrition-edible` | 1000 г картофеля, ediblePartRatio=0.85 | расчёт от 850 г |
| `shopping-roundup` | потребность 700 г филе, упаковка 500 г | packageQuantity=2 |
| `shopping-staple` | в pantry соль со статусом STAPLE | соль отсутствует в списке |
| `planner-deterministic` | фиксированный каталог + seed RNG=42 | побайтово одинаковый план при повторном прогоне |
| `planner-norepeat` | repeatPolicy=NO_REPEAT, 7 дней | ни одного повторного recipeId |
| `fit-budget` | корзина 6500 ₽, лимит 5800 ₽ | итог ≤ 5800 ₽ после proposals |

Любое изменение ожидания в fixture — только с отдельным обоснованием в PR («почему новое значение правильное»).

## 3. Конвенции тестов

- Именование: `<unit>.<behavior>.test.ts`; describe = сущность, it = поведение на русском или английском, единообразно в пределах пакета.
- Integration-тесты: отдельная БД на прогон (Testcontainers), `migrate deploy` в beforeAll, фабрики данных через `tests/factories`.
- Ни один тест не зависит от текущей даты: время инжектируется (`clock` / `jest.useFakeTimers`-аналог для Vitest).
- Сроки годности в тестах — только относительные (`today()+2`), никаких хардкод-дат.
- Покрытие: доменные пакеты (`nutrition`, `recommendation`) ≥ 90% ветвей; api-модули ≥ 70% строк; ui — покрытие критических компонентов состояний.

## 4. E2E-сценарии (Playwright)

Каждый сценарий — независим, с собственным seed-пользователем, viewport 390×844 (iPhone 14), второй прогон — WebKit.

| # | Сценарий | Ключевые assert-ы |
| --- | --- | --- |
| E1 | Регистрация | cookie установлена (HttpOnly), редирект на /today |
| E2 | Онбординг 7 шагов | данные сохранены, видны в /profile |
| E3 | Добавление продуктов | поиск «помидор» → добавлен, бейдж срока корректного цвета |
| E4 | Рекомендация «на сегодня» | ровно 3 карточки, у каждой — плашка объяснения |
| E5 | Недельный план | job-прогресс → план: 7 дней × N приёмов, КБЖУ-бары > 0 |
| E6 | Замена блюда | bottom-sheet 3 альтернативы → замена → totals обновились |
| E7 | Список покупок | группы по отделам, сумма > 0, упаковки округлены |
| E8 | Отметки покупок | optimistic check → перезагрузка → состояние сохранено |
| E9 | План заготовки | таймлайн задач, параллельные группы помечены |
| E10 | Offline | авиарежим: /shopping и активный план открываются; offline-плашка видна; отметка purchased синхронизируется после сети |

Артефакты при падении: screenshot + trace + video. Хранение 14 дней.

## 5. Нефункциональная верификация

### 5.1. Производительность


- `POST /recommendations/today` < 500 мс (p95, seed-каталог 300 рецептов).
- Генерация недельного плана < 60 сек (job, 7×3).
- `GET /recipes`, `GET /pantry-items` — p95 < 300 мс при 20 RPS / 60 сек, 0 ошибок 5xx.
- Lighthouse на /today: Performance ≥ 80, Accessibility ≥ 95, Best Practices ≥ 90.


### 5.2. Безопасность (чек-лист на релиз)

- [ ] gitleaks чист по всей истории.
- [ ] Все мутации требуют CSRF-заголовок (тест 403 без него).
- [ ] Все ресурсы проверяют householdId из сессии (integration: чужой id → 404).
- [ ] Rate limit на /auth/* (тест 429 на 11-й запрос).
- [ ] Security headers на всех ответах (curl -I).
- [ ] 3000/3001/5432/6379 не слушают внешний интерфейс (`ss -tlnp`).
- [ ] Пароли — Argon2id; токены сессий в БД — только хеши.
- [ ] Sentry-scrubbing: в событиях нет cookie/Authorization/email.

- [ ] npm audit: 0 critical/high без documented-исключения.


### 5.3. Доступность (a11y)

- Контрасты ≥ 4.5:1 (отчёт в PR для MC-012, далее — при изменении токенов).
- Клавиатурная навигация по 5 табам и wizard (Tab/Shift+Tab/Enter/Escape).
- Видимый focus-ring; touch-target ≥ 44px; axe-core в e2e на /today и /plan — 0 critical-нарушений.

## 6. CI/CD-гейты

```text
PR pipeline (блокирующий):
  install → lint → format:check → typecheck → unit+component → integration → build → gitleaks
Nightly (неблокирующий, алерт в канал):
  e2e (Chromium+WebKit) → npm audit → lighthouse-ci
Release (на тег v*):
  всё выше + load smoke + backup/restore drill
```

Merge в `main` — только через PR с зелёным blocking-pipeline. Релизный тег ставится только после релизного чек-листа MC-075.

## 7. Ручной QA (перед каждым релизным тегом)

Устройства: iOS Safari (реальный iPhone) + Android Chrome (реальный Android). Каждый юзкейс UC-01…UC-12 из PRD §1.3 прогоняется пошагово; результат — подписанный чек-лист со скриншотами в `docs/qa/<version>/`.

Обязательные визуальные проверки: светлая/тёмная тема; safe-area на iPhone (таб-бар, bottom-sheet); skeleton-загрузки; empty-states; ошибки сети (toast + rollback); дисклеймер КБЖУ виден на экране рецепта и дневной сводке.

## 8. Определение «готово» для релиза

Релизный тег ставится тогда и только тогда, когда: (1) все задачи релизной точки смержены с пройденным DoD; (2) nightly e2e зелёный 3 запуска подряд; (3) ручной QA-чек-лист подписан; (4) backup/restore drill выполнен в текущем релизном цикле; (5) security-чек-лист §5.2 закрыт.
